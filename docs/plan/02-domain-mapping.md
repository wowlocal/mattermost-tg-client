## Identifiers

All mappings live in a persistent **ID map** in the app‑group container, so the notification and share extensions can read it. It is either a custom Postbox table or a small SQLite file next to Postbox; decide in Phase 0.

### Peers

Telegram identifies a peer as `PeerId(namespace, id: Int64)`. Mattermost uses 26‑character string IDs.

- Allocate local `Int64` IDs sequentially per namespace and store `mattermostId ↔ PeerId`.
- User → `CloudUser` namespace.
- Public/private channel → `CloudChannel` namespace.
- GM → `CloudGroup` namespace.
- DM channel → the **other user's** peer, because Telegram's private chat *is* the user peer. Store `dmChannelId ↔ userPeerId` separately.
- Self‑DM → own user peer (renders as Saved Messages).

### Message IDs

**This is the highest technical risk. Decide it in Phase 0, Spike C.**

Telegram assumptions (to verify):

- `MessageId = (peerId, namespace, id: Int32)`.
- `MessageIndex` sorts by `timestamp` (Int32 seconds), then namespace, then id.
- History holes (gaps not yet loaded) are tracked as **Int32 ID ranges** per peer and namespace.
- Read state is "max read ID".

Mattermost: 26‑character string IDs, `create_at` in milliseconds, cursor paging by post ID (`before`/`after`) or by time (`since`).

Requirements for a mapping:

1. Unique per peer.
2. Monotonic with `create_at`, so ID order matches time order.
3. Works when loading older history, newer history, and **jumping to a permalink** deep in the past (this creates disconnected "islands").
4. Handles imported history (e.g. Slack imports) with arbitrary old `create_at`.
5. Never runs out.

#### Option 1: IDs derived from timestamps

`id = (create_at_s − epoch) × K + slot`

- Stateless and simple.
- **Runs out of Int32 range.** With K = 4 and a 2015 epoch, it overflows around 2032.
- Breaks on imported history older than the epoch.
- Needs probing when more than K posts land in one second (bots).

Rejected as the primary scheme.

#### Option 2: sparse allocation with a stored map (recommended)

IDs are local and stored in the ID map. `STEP = 16`.

| Situation | Rule |
|---|---|
| First post seen in a channel | `id = 2^30` (middle of the positive Int32 range) |
| Page extending history from an anchor (normal paging, filling a hole from one side) | Consecutive IDs spaced by `STEP` from the anchor, moving away from it |
| Single late insert between known neighbours `A < p < B` | Midpoint of `A` and `B` |
| Permalink jump into unloaded history | New island placed in the gap between nearest known neighbours, proportionally to time, leaving holes on both sides |
| Gap exhausted (no room left) | Renumber the smaller island in one Postbox transaction (delete and re‑insert). Expected to be rare. |

- Capacity: about 2^31 / 16 ≈ 134 million posts per channel.
- A hole is the ID gap between two islands. Filling it loads posts with Mattermost cursors (`before`/`after` the boundary post's ID) and allocates IDs inside the hole's range.
- When a loaded post already has an ID (the other island's edge), the hole is closed.

#### Option 3: bypass Postbox holes

A custom history loader where Postbox is only a cache, with no hole semantics. This means more changes to the chat screen. Fallback if option 2 fights Postbox too much.

#### Spike C tests

- Initial page.
- Backward paging over 10,000 posts.
- Permalink jump into old history, then paging until the islands join.
- Late‑arriving post between adjacent posts.
- Many posts within the same second.
- Imported posts from 2013.
- Property test: random interleavings of all of the above keep IDs unique and ordered by `(create_at, postId)`.

### Timestamps

Telegram timestamps are Int32 seconds. Keep the full `create_at` (ms) in the ID map. Ordering within the same second follows ID order, which option 2 keeps consistent with milliseconds.

### Pending (outgoing) messages

- While sending, the message lives in Telegram's **Local** namespace with a `pending_post_id` stored as an attribute.
- On success, it is replaced by the **Cloud** message with an allocated ID.
- If a WebSocket `posted` event arrives before the HTTP response, deduplicate on `pending_post_id`.

## Read state and unread counts

| Telegram field (assumed `PeerReadState.idBased`) | Source |
|---|---|
| `maxIncomingReadId` | Local ID of the newest known post with `create_at ≤ member.last_viewed_at` |
| `maxOutgoingReadId` | `0` (single check). Optional for DMs: derive from the other member's `last_viewed_at`. That is a product and privacy decision: Mattermost itself doesn't show it. |
| `maxKnownId` | Newest local ID |
| `count` | `channel.total_msg_count − member.msg_count` (use the `_root` variants when collapsed threads are on) |
| Mention badge | `member.mention_count` (or `mention_count_root`) |

- Mark read: `POST /channels/members/me/view`.
- Mark unread from a post: `POST /users/me/posts/{post_id}/set_unread`.
- Muted channels (`notify_props.mark_unread = mention`) map to Telegram mute.

## Teams and sidebar

**Recommended mapping: one generated chat folder per team.**

- Each folder includes all DMs (through the private‑chat categories), plus an explicit `includePeers` list of that team's channels and all GMs.
- An "All" tab shows everything.
- Folders are regenerated when membership changes.
- Folders are **local only**: disable Telegram's server folder sync.
- Check for client‑side `includePeers` limits; Telegram's server enforces ~100–200, and the client may hard‑code it too.

Alternative: one Telegram account per team. Rejected because DMs would be duplicated across accounts and the multi‑account switcher isn't meant for that.

Other sidebar mappings:

- Favorites → pinned chats in the team folder.
- Custom categories → deferred. Possible later as "Team · Category" folders or as section headers in the chat list.

## Threads

- `post.root_id` → `threadId` = local ID of the root post.
- Reply count and participants (`reply_count`, `participants`, `last_reply_at`) → the reply‑thread attribute on the root message. This drives the "N replies" button.
- Opening a thread → Telegram's reply‑thread chat location.
- **Collapsed reply threads (CRT):** with CRT on, replies must be hidden from the main channel history. Postbox's main history for non‑forum groups probably includes thread messages, so this needs a "threadId == nil" filter on the main history view. Forum topics may already have a similar mechanism.
  - MVP: show replies inline with a reply header (the "CRT off" presentation).
  - Phase 3: real CRT plus a new Threads list screen (`GET /users/me/teams/{team_id}/threads`).

## Text

Mattermost uses markdown text. Telegram uses plain text plus entities.

| Markdown | Telegram |
|---|---|
| `**bold**` | Bold entity |
| `_italic_` / `*italic*` | Italic entity |
| `~~strike~~` | Strikethrough entity |
| `` `code` `` | Code entity |
| ```` ```lang ```` blocks | Pre entity with language |
| `> quote` | Block quote entity |
| `[text](url)`, autolinks | Text URL and URL entities |
| `@username` | Mention, resolved to a user peer when known |
| `~channel-name` | Custom link entity that opens the channel |
| `@channel`, `@here`, `@all` | Highlighted mention |
| `:emoji_name:` | Unicode emoji, or a custom emoji entity |
| Headings, lists, tables, LaTeX, inline images | Custom **markdown block bubble** (MattermostUI); plain‑text fallback in MVP |

- Parse markdown with a CommonMark parser in `MattermostSync`, at write time, and store the entities on the message.
- Outgoing messages: send the raw text the user typed. Telegram's composer formatting (bold, etc.) is turned back into markdown.

## Media

- `post.metadata.files` → `TelegramMediaImage` (images, with dimensions and a thumbnail) or `TelegramMediaFile` (video, audio, documents).
- A new `MattermostFileResource(fileId, variant: original | thumbnail | preview)` is fetched by a `MediaBox` fetcher that adds the auth header.
- Avatars: `MattermostAvatarResource(userId, lastPictureUpdate)` from `/users/{id}/image`.
- Custom emoji: `MattermostEmojiResource(emojiId)` from `/emoji/{id}/image`.

## Users and presence

- Mattermost user → `TelegramUser`:
  - first and last name, `username`
  - photo through the avatar resource
  - bots flagged as bots
  - display‑name settings (username vs full name vs nickname) applied when building the user
- Presence:

  | Mattermost status | Telegram presence |
  |---|---|
  | online | "online until now + 60 s", refreshed by events |
  | away | "recently", or online plus an away badge (decide in design) |
  | dnd | online plus a DND badge (new) |
  | offline | "last seen" from `last_activity_at` |
