# Relay calls with Telegram's native call UI

Status: plan, 2026-11-08. Supersedes the SwiftUI call window from the first pass (`RelayCallView`,
`RelayCallWindow`). Media stays on self-hosted LiveKit. The user interface is Telegram's own, on both
clients, driven by LiveKit-backed adapters behind Telegram's existing call protocols.

## What the owner asked for

- Exact Telegram look and feel for calls. Reuse Telegram's call screens; do not imitate them.
- 1:1 calls ring (CallKit on iOS, the incoming call window on macOS, Telegram's tones).
- Room/group calls exactly like Telegram's group calls and video chats.
- Camera video, not only screen sharing.

## Who rings

| Mattermost channel | Telegram equivalent | Rings |
| --- | --- | --- |
| Direct message (`D`) | 1:1 call: `PrivateCallScreen` (iOS), `PeerCallScreen` (macOS) | the other user, all devices |
| Group message (`G`) | group call (`VideoChatScreen` / `GroupCallUIController`) | every other member |
| Public/private channel (`O`/`P`) | video chat with the chat-header join panel | nobody; members join from the panel |

## Architecture

```
Telegram UI (unchanged screens)        iOS: CallController / PrivateCallScreen, VideoChatScreen, CallKit, status bar
        │ PresentationCall / PresentationGroupCall (AccountContext)      macOS: PeerCallScreen via a peer-call protocol,
        │                                                                     GroupCallContext(call: PresentationGroupCall)
Platform adapters  (iOS: submodules/RelayCalls/Sources/RelayCallsTelegram; macOS: packages/RelayTelegramCalls)
        │ RelayDirectCall / RelayGroupCall controllers, RelayRoomEngine, video frame sinks
Shared core        submodules/RelayCalls (RelayCallsCore: REST + events, Foundation only; RelayCalls: LiveKit engine)
        │ REST + WebSocket events (custom_org.relaychat.calls_*) + VoIP push
Mattermost plugin  infra/relay-calls  ──►  LiveKit (rooms, tokens, webhooks)
```

MattermostSync (shared by both clients) delivers plugin events, keeps `CachedChannelData.activeCall` for the
join panel, maps call-record posts to Telegram's call service messages, and marks DM users as callable.

## Wire contract (plugin `org.relaychat.calls`, version 2)

All routes are under `/plugins/org.relaychat.calls`, authenticated by the Mattermost session. Times are Unix ms.
`device_id` is a stable per-install, per-account UUID generated by the client.

### Call object

```json
{
  "id": "…", "channel_id": "…", "room": "relay_…",
  "kind": "direct|group|channel",
  "state": "ringing|active|ended",
  "video": false,
  "started_by": "<caller user id>", "started_at": 0,
  "ring_expires_at": 0,
  "end_reason": "missed|cancelled|declined|busy|hangup|ended|failed",
  "end_at": 0, "duration_ms": 0,
  "participants": 0,
  "participant_ids": ["<user id>", "…"],
  "invitees": {"<user id>": "ringing|received|accepted|declined|busy|missed"},
  "post_id": "…",
  "can_end": true
}
```

`participants` stays the connected device count (version 1 clients read it). `participant_ids` are distinct
connected users. `invitees` is present for `direct`/`group` calls that rang (omitted when empty). `ring_expires_at`
only while ringing. `end_*` and `duration_ms` only when ended (`duration_ms` counts from the first answer, `0`
when nobody answered). `can_end` is computed for the caller of the request; in event payloads it is true only for
the starter.

A call is `ringing` exactly while some invitee is still `ringing`/`received`: a `group` call stays `ringing` after
the first answers until the others answer, decline or time out, then turns `active`. When a call ends, invitees
still ringing become `missed` (also on `cancelled`).

### Routes

| Method and route | Body | Result |
| --- | --- | --- |
| `GET /config` | | `{enabled, version: 2, max_participants, screen_sharing, camera: true, ringing: true, ring_timeout_seconds}` |
| `GET /channels/<id>` | | `{call}`: current call or `null` (unchanged) |
| `POST /channels/<id>/join` | `{call_id?, device_id?}` | `{url, token, call}`; joins an active call (any kind) or starts a call without ringing (a channel call; in `D`/`G`, a `direct`/`group` call with no invitees, for version 1 clients); an invitee whose devices ring answers as with `accept` |
| `POST /channels/<id>/ring` | `{video, device_id}` | `{url, token, call}`; `D`/`G` only (`400` otherwise, also when there is nobody to ring); `409` with the call if one is already ringing or active there; when the `direct` invitee is busy, `200` with the call already `ended` (`busy`) and an empty `token` |
| `POST /channels/<id>/end` | `{call_id}` | end for everyone (unchanged permissions); `end_reason` `cancelled` if nobody answered, `hangup` for `direct`, else `ended` |
| `GET /calls/<id>` | | the call object itself (not wrapped); `404` once forgotten (about 10 minutes after the end) |
| `GET /calls/active` | | `{calls: [call, …]}`, newest first: every ringing or active call in channels the user belongs to (the client finds its own rings via `invitees[me]` = `ringing`/`received`; the rest feed the join panel) |
| `POST /calls/<id>/received` | `{device_id}` | `204`; invitee device shows the call ("Ringing…" for the caller) |
| `POST /calls/<id>/accept` | `{device_id}` | `{url, token, call}`; first device wins (compare-and-set); `409` if no longer ringing for this user (also after the ring timeout) |
| `POST /calls/<id>/decline` | `{device_id, reason: "declined"\|"busy"}` | `204` (repeating the same decline is `204` too) |
| `POST /calls/<id>/hangup` | `{device_id}` | `204`; caller before anyone answered → `cancelled` (`direct` and `group`); `direct` after the answer → ends (`hangup`) for both; an invitee still ringing → declines; otherwise leave (that device, or every device of the user without `device_id`, is removed from the room) |
| `POST /devices/voip` | `{device_id, token, environment: "sandbox"\|"production", bundle_id}` | `204` |
| `DELETE /devices/voip/<device_id>` | | `204` |

`received`, `accept` and `decline` on a call that no longer rings for the user answer `409`. Every `409` body is
`{message, call}` except the version 1 stale `call_id` conflict (`{message}`). Other errors are `{message}`.

Rules: a `direct` call ends with `declined` when the callee declines, `busy` when every invitee is busy (another
ringing or active call, or a device answered `busy`), `missed` when the ring timeout (default 45 s) passes,
`cancelled` when the caller hangs up first. A `group` call stays alive while anyone is connected; invitees who do
not answer become `missed`. Ring expiry survives plugin restarts (state in KV, swept by a ticker). A room that
finishes ends the call with `hangup` (answered `direct`), `failed` (still ringing) or `ended`. A device leaving the
room never ends a call by itself: the remaining `direct` client hangs up when its peer is gone.

LiveKit tokens: identity `<user id>:<device id>`, name = display name, sources `microphone`, `camera`,
`screen_share`, `screen_share_audio`.

### WebSocket events

Mattermost delivers them as `custom_org.relaychat.calls_<name>`; `data` is the JSON object below.

| Name | Recipients | Data |
| --- | --- | --- |
| `incoming` | each invitee (all sessions) | `{call, caller: {id, username, display_name}}` |
| `call_state` | caller and invitees | `{call, user_id, device_id, action}`; action `received\|accepted\|declined\|busy\|missed\|cancelled\|hangup\|joined\|left` |
| `call_updated` | channel members and invitees | `{call}` |
| `call_ended` | channel members and invitees | `{call}` (state `ended`, `end_reason`) |

`call_updated` and `call_ended` reach each recipient once: per user to the caller and invitees, and to the channel
without them. Their data also carries `channel_id` and `call_id` (version 1 clients read them). `call_state` is not
sent for `channel` calls. A client must fetch `GET /calls/active` after (re)connecting: events are not replayed.

### VoIP push (iOS)

The plugin sends directly to APNs (`apns-push-type: voip`, topic `<bundle_id>.voip`, priority 10, expiration =
`ring_expires_at`, collapse id = call id) with the Relay `.p8` key from the plugin's secret config. Payload:

```json
{"relay_call": {"v": 2, "call_id": "…", "channel_id": "…", "caller_id": "…", "caller_name": "…",
 "video": false, "ring_expires_at": 0, "server_url": "<SiteURL>", "recipient_id": "…"}}
```

Never a VoIP push for "cancel": iOS requires every VoIP push to be reported to CallKit. A device woken by a
ring checks `GET /calls/<id>` and ends the CallKit call if it is no longer ringing for it. Tokens answering
`410`/`BadDeviceToken`/`Unregistered` are removed. A registration belongs to the Mattermost session that made it
and is dropped once that session is gone (logout); registering a token under a new `device_id` replaces the old
entry. `environment` picks `api.sandbox.push.apple.com` or `api.push.apple.com`. Without a configured key the
plugin sends no VoIP pushes (rings still arrive over WebSocket).

### Call records

The plugin posts one `custom_relay_call` post per call and updates it (`UpdatePost`) when the call ends:
`props.relay_call = {v: 2, call_id, kind, video, state, started_by, end_reason, duration_ms, started_at, end_at}`,
with a short plain message for other Mattermost clients ("Call", "Video call", "Group call" while live; "Missed
call", "Cancelled call", "Declined call", "Call · busy", "Video call · 3 min" when ended). The post is created at
ring/start by the caller (only while the `AnnounceCalls` setting is on) and Mattermost's own push for it is
suppressed, so a DM ring is not doubled by an alert; invitees who missed the ring get a "Missed call from X"
push instead (not when the server sends id-only push contents). Relay maps it to `TelegramMediaAction.phoneCall`
(`direct`) or `.groupPhoneCall` (`group`/`channel`), so the chat shows Telegram's call service messages.

### `RelayCallsCore` (Foundation only, iOS 15 / macOS 13)

  endAt: Int64?, durationMs: Int64?, participants, participantIds, invitees: [String: RelayInviteeState]?, postId:
  String?, canEnd`; helpers `isRinging(for: userId)`, `isLive`, `ringExpiryDate`.
- `RelayInviteeState` (`.ringing/.received/.accepted/.declined/.busy/.missed`, `isRinging`), `RelayCallEndReason`,
  `RelayCallJoin {url, token, call}`, `RelayCallsConfiguration {enabled, version, maxParticipants, screenSharing,

(fixed values, as before) or `init(serverURL:token: @escaping () -> String?, session: @escaping () -> URLSession)`
(looked up per request; MattermostSync passes the account's token and `MattermostURLSession.current`). Routes:
`configuration()`, `call(channelId:) -> RelayCall?`, `join(channelId:callId:deviceId:)`, `ring(channelId:video:deviceId:)`
(a running call throws `RelayCallsError.callInProgress(RelayCall)`), `end(channelId:callId:)`, `call(id:) -> RelayCall?`

`ws`/`http` only for `localhost`, `127.x.x.x` and `::1` (`RelayCallsClient.isAllowedMediaURL`). Errors:

Media engine protocol (`@MainActor protocol RelayMediaEngine`): `snapshot: RelayMediaSnapshot`, `onChange:

RelayMediaConnectionState (.disconnected/.connecting/.connected/.reconnecting), participants (local first), local,
remote}`; `RelayMediaParticipant {identity, name, isLocal, isSpeaking, audioLevel (0…1), connectionQuality:
RelayConnectionQuality, microphone/camera/screenShare: RelayMediaTrack? {sid, isMuted, width, height, isLive},
joinedAt, userId, isMicrophoneEnabled, isCameraEnabled, isScreenSharing}`. Timers go through `RelayCallScheduler`
(default `RelaySystemScheduler.shared`); observations return a `RelayCancellable` (cancelled on `cancel()` or deinit).

`@MainActor final class RelayDirectCall` (1:1, `kind: direct`):

- Create: `.outgoing(api:engine:ownUserId:deviceId:channelId:peerUserId:video:scheduler:)`,
  `.incoming(api:engine:ownUserId:deviceId:call:)` (the `incoming` event or an own ring in `.activeCalls`),
  `.incoming(api:engine:ownUserId:deviceId:push:)` (VoIP push; `start()` first checks `GET /calls/<id>` and ends the
  call if it no longer rings for this user). `static declineBusy(api:callId:deviceId:)` declines a ring this device
  cannot take without a controller.
- Act: `start()` (outgoing: rings and connects the media right away; incoming: reports `received`, starts the local
  ring expiry), `accept()`, `decline(reason:)`, `hangup()` (declines an unanswered incoming ring, cancels an
  unanswered outgoing one, ends an answered call for both), `setMuted(_:)`, `setCameraEnabled(_:)` (either side, any
  time; a `video` call starts with the camera on), `setScreenShare(enabled:)`, `handle(_ event: RelayCallsEvent)`
  (feed every event of the account; other calls' events are ignored).
- Observe: `state`, `snapshot: Snapshot {state, call, callId, channelId, peerUserId, isOutgoing, isVideo, isMuted,
  isCameraEnabled, isScreenSharing, mediaState, local, remote}`, `observe(_:) -> RelayCancellable`.
- `State` mirrors Telegram's `PresentationCallState.State`: `.requesting(ringing: Bool)` (outgoing; `true` once a
  callee device reported `received`: ringback), `.ringing` (incoming), `.connecting` (answered, the other device not
  in the room yet), `.active(since: Date)`, `.reconnecting(since: Date)` (media reconnecting, or the other device
  dropped out after the call was up), `.terminated(EndReason, duration: TimeInterval?)` (duration from the answer;
  the plugin's `duration_ms` when it sent one). An answered call that stays `.connecting` for
  `RelayDirectCall.connectTimeout` (30 s) or `.reconnecting` for `reconnectTimeout` (60 s) ends as `.failed` and
  hangs up.
- `EndReason` and the suggested Telegram mapping (`CallSessionTerminationReason`): `.hangup` (this device; an
  unanswered outgoing call was cancelled) and `.remoteHangup` → `.ended(.hungUp)`; `.declined` (callee declined) and
  `.busy` → `.ended(.busy)`; `.missed` → `.ended(.missed)`; `.cancelled` (incoming: the caller hung up first) →
  `.ended(.missed)`; `.declinedLocally` → `.ended(.hungUp)`; `.answeredElsewhere`/`.declinedElsewhere` → end the
  CallKit call as answered/declined elsewhere (`CXCallEndedReason.answeredElsewhere`/`.declinedElsewhere`); `.ended`
  → `.ended(.hungUp)`; `.failed(String)` → `.error(.generic)`.

`@MainActor final class RelayGroupCall` (`group` and `channel` calls):

- Create: `.join(api:engine:ownUserId:deviceId:channelId:callId:kind:scheduler:)` (joins the channel's call or
  starts a channel call; `callId` from the join panel), `.ring(api:engine:ownUserId:deviceId:channelId:video:)`
  (group message: rings the other members; joins the running call if there is one),
  `.incoming(api:engine:ownUserId:deviceId:call:)` / `.incoming(…push:)` (a group ring for this user).
- Act: `start()`, `accept()` (a ring that stopped meanwhile joins the running call), `decline(reason:)`, `leave()`,
  `endForEveryone() async throws` (`snapshot.canEnd`), `setMuted(_:)`, `setCameraEnabled(_:)`,
  `setScreenShare(enabled:)`, `handle(_:)`.
- `State`: `.ringing` (incoming ring), `.connecting`, `.connected`, `.reconnecting`, `.ended(EndReason)` with
  `.left`, `.ended`, `.declined`, `.missed`, `.answeredElsewhere`, `.removed`, `.failed(String)`.
- `snapshot: Snapshot {state, call, callId, channelId, kind, participants, invitees, isMuted, isCameraEnabled,
  isScreenSharing, mediaState, canEnd}`; `participants: [Participant]`, one per Mattermost user (Telegram keys by
  peer): `userId, name, isSelf, devices: [RelayMediaParticipant] (this device first), isSpeaking (any device),
  audioLevel (loudest), isMicrophoneEnabled (any), camera/screenShare: Video? {identity, track, isLocal} (a live
  track of any device, this device first), connectionQuality (best), joinedAt (earliest)`; the own user first, then
  by join time. `static mergeParticipants(_:ownUserId:)` is the pure merge.

Threading: controllers and the engine are main-actor objects; feed events from `MattermostSync.relayCallEvents`
observed on the main queue.

### `RelayCalls` (LiveKit 2.19)

- `@MainActor final class RelayRoomEngine: RelayMediaEngine`: `init(options: Options)` with `Options(usesExternalCamera:
  cameraDimensions: CMVideoDimensions (1280×720), cameraFPS (30), usesBroadcastExtension (true))`. `room: Room`,
  `externalCamera: RelayExternalCamera?`. Rooms use adaptive stream, dynacast, simulcast camera/screen tracks with
  H.264 preferred (VP8 backup). Camera: `switchCamera() -> AVCaptureDevice.Position`, `setCameraPosition(_:)`,
  `currentCameraPosition` (LiveKit's capturer; front by default on iOS). Screen: iOS `setScreenShare(enabled:)` uses
  the ReplayKit broadcast extension (as before, never ScreenCaptureKit); macOS `setScreenShare(enabled: true)` shares
  the main display, `screenShareSources()`, `shareScreen(source:)`, `RelayRoomEngine.displayName(of:)`. Video:
  `videoTrack(sid:) -> VideoTrack?`, `attach(_ sink:toTrackSid:) -> Bool` (false until subscribed: retry on the next
  `onChange`), `detach(_:fromTrackSid:)`.
- `RelayExternalCamera` (thread-safe): `push(_ pixelBuffer: CVPixelBuffer, rotation: RelayVideoRotation,
  timestampNs: Int64?)` or `push(_ sampleBuffer:)` from the app's capturer (NV12, BGRA or ARGB);
  `onActiveChange: ((Bool) -> Void)?` asks the app to start/stop capturing; `isActive`. `setCamera(enabled: true)`
  creates a `BufferCapturer` track, waits up to 5 s for the first frame (LiveKit needs its dimensions), then publishes.
- `RelayVideoSink(onFrame: (RelayVideoFrame) -> Void)`: a LiveKit `VideoRenderer`, called on WebRTC's thread.
  `RelayVideoFrame {buffer: .pixelBuffer(CVPixelBuffer) | .i420(RelayI420Buffer), width, height (before rotation),
  rotation: RelayVideoRotation (.rotation0/90/180/270), timestampNs}`; `RelayI420Buffer {width, height, chromaWidth,
  chromaHeight, strideY/U/V, withPlanes { y, u, v in … }, y/u/v: Data copies}`. No BGRA conversion. Adaptive stream:
  set `isVisible` and `viewSize` on the main actor.
- iOS `RelayCallKitAudio`: `prepare()` once before any room connects (turns off LiveKit's automatic `AVAudioSession`
  configuration, engine availability `.none`), `didActivate(_:configureSession:)` / `didDeactivate(_:)` from the
  `CXProviderDelegate`, `activateWithoutCallKit()`, `isEngineAvailable`, `setSpeakerOutputPreferred(_:)`.

The first pass's `RelayCallSession`/`RelayCallView` still compile; the adapters remove them.
