# Relay calls with Telegram's native call UI

Status: plan, 2026-11-08. Supersedes the SwiftUI call window from the first pass (`RelayCallView`,
`RelayCallWindow`). Media stays on self-hosted LiveKit. The user interface is Telegram's own, on both
clients, driven by LiveKit-backed adapters behind Telegram's existing call protocols.

## What the owner asked for

- Exact Telegram look and feel for calls. Reuse Telegram's call screens; do not imitate them.
- 1:1 calls ring (CallKit on iOS, the incoming call window on macOS, Telegram's tones).
- Room/group calls exactly like Telegram's group calls and video chats.
- Camera video, not only screen sharing.

## Who rings

| Mattermost channel | Telegram equivalent | Rings |
| --- | --- | --- |
| Direct message (`D`) | 1:1 call: `PrivateCallScreen` (iOS), `PeerCallScreen` (macOS) | the other user, all devices |
| Group message (`G`) | group call (`VideoChatScreen` / `GroupCallUIController`) | every other member |
| Public/private channel (`O`/`P`) | video chat with the chat-header join panel | nobody; members join from the panel |

## Architecture

```
Telegram UI (unchanged screens)        iOS: CallController / PrivateCallScreen, VideoChatScreen, CallKit, status bar
        │ PresentationCall / PresentationGroupCall (AccountContext)      macOS: PeerCallScreen via a peer-call protocol,
        │                                                                     GroupCallContext(call: PresentationGroupCall)
Platform adapters  (iOS: submodules/RelayCalls/Sources/RelayCallsTelegram; macOS: packages/RelayTelegramCalls)
        │ RelayDirectCall / RelayGroupCall controllers, RelayRoomEngine, video frame sinks
Shared core        submodules/RelayCalls (RelayCallsCore: REST + events, Foundation only; RelayCalls: LiveKit engine)
        │ REST + WebSocket events (custom_org.relaychat.calls_*) + VoIP push
Mattermost plugin  infra/relay-calls  ──►  LiveKit (rooms, tokens, webhooks)
```

MattermostSync (shared by both clients) delivers plugin events, keeps `CachedChannelData.activeCall` for the
join panel, maps call-record posts to Telegram's call service messages, and marks DM users as callable.

## Wire contract (plugin `org.relaychat.calls`, version 2)

All routes are under `/plugins/org.relaychat.calls`, authenticated by the Mattermost session. Times are Unix ms.
`device_id` is a stable per-install, per-account UUID generated by the client.

### Call object

```json
{
  "id": "…", "channel_id": "…", "room": "relay_…",
  "kind": "direct|group|channel",
  "state": "ringing|active|ended",
  "video": false,
  "started_by": "<caller user id>", "started_at": 0,
  "ring_expires_at": 0,
  "end_reason": "missed|cancelled|declined|busy|hangup|ended|failed",
  "end_at": 0, "duration_ms": 0,
  "participants": 0,
  "participant_ids": ["<user id>", "…"],
  "invitees": {"<user id>": "ringing|received|accepted|declined|busy|missed"},
  "post_id": "…",
  "can_end": true
}
```

`participants` stays the connected device count (version 1 clients read it). `participant_ids` are distinct
connected users. `invitees` is present for `direct`/`group`. `ring_expires_at` only while ringing. `end_*` and
`duration_ms` only when ended (`duration_ms` counts from the first answer). `can_end` is computed for the caller of
the request.

### Routes

| Method and route | Body | Result |
| --- | --- | --- |
| `GET /config` | | `{enabled, version: 2, max_participants, screen_sharing, camera: true, ringing: true, ring_timeout_seconds}` |
| `GET /channels/<id>` | | current call or `null` (unchanged) |
| `POST /channels/<id>/join` | `{call_id?, device_id?}` | `{url, token, call}`; joins an active call (any kind) or starts a channel call |
| `POST /channels/<id>/ring` | `{video, device_id}` | `{url, token, call}`; `D`/`G` only (`400` otherwise); `409` with the call if one is already active there |
| `POST /channels/<id>/end` | `{call_id}` | end for everyone (unchanged permissions) |
| `GET /calls/<id>` | | call object (`404` once forgotten) |
| `GET /calls/active` | | every ringing or active call in channels the user belongs to (the client finds its own rings via `invitees[me]` = `ringing`/`received`; the rest feed the join panel) |
| `POST /calls/<id>/received` | `{device_id}` | `204`; invitee device shows the call ("Ringing…" for the caller) |
| `POST /calls/<id>/accept` | `{device_id}` | `{url, token, call}`; first device wins (compare-and-set); `409` if no longer ringing for this user |
| `POST /calls/<id>/decline` | `{device_id, reason: "declined"\|"busy"}` | `204` |
| `POST /calls/<id>/hangup` | `{device_id}` | `204`; caller while ringing → `cancelled`; `direct` while active → ends (`hangup`) for both; `group` → leave |
| `POST /devices/voip` | `{device_id, token, environment: "sandbox"\|"production", bundle_id}` | `204` |
| `DELETE /devices/voip/<device_id>` | | `204` |

Rules: a `direct` call ends with `declined` when the callee declines, `busy` when every invitee is busy (another
ringing or active call, or a device answered `busy`), `missed` when the ring timeout (default 45 s) passes,
`cancelled` when the caller hangs up first. A `group` call stays alive while anyone is connected; invitees who do
not answer become `missed`. Ring expiry survives plugin restarts (state in KV, swept by a ticker).

LiveKit tokens: identity `<user id>:<device id>`, name = display name, sources `microphone`, `camera`,
`screen_share`, `screen_share_audio`.

### WebSocket events

Mattermost delivers them as `custom_org.relaychat.calls_<name>`; `data` is the JSON object below.

| Name | Recipients | Data |
| --- | --- | --- |
| `incoming` | each invitee (all sessions) | `{call, caller: {id, username, display_name}}` |
| `call_state` | caller and invitees | `{call, user_id, device_id, action}`; action `received\|accepted\|declined\|busy\|missed\|cancelled\|hangup\|joined\|left` |
| `call_updated` | channel members | `{call}` |
| `call_ended` | channel members and invitees | `{call}` (state `ended`, `end_reason`) |

A client must fetch `GET /calls/active` after (re)connecting: events are not replayed.

### VoIP push (iOS)

The plugin sends directly to APNs (`apns-push-type: voip`, topic `<bundle_id>.voip`, priority 10, expiration =
`ring_expires_at`, collapse id = call id) with the Relay `.p8` key from the plugin's secret config. Payload:

```json
{"relay_call": {"v": 2, "call_id": "…", "channel_id": "…", "caller_id": "…", "caller_name": "…",
 "video": false, "ring_expires_at": 0, "server_url": "<SiteURL>", "recipient_id": "…"}}
```

Never a VoIP push for "cancel": iOS requires every VoIP push to be reported to CallKit. A device woken by a
ring checks `GET /calls/<id>` and ends the CallKit call if it is no longer ringing for it. Tokens answering
`410`/`BadDeviceToken` are removed.

### Call records

The plugin posts one `custom_relay_call` post per call and updates it (`UpdatePost`) when the call ends:
`props.relay_call = {v: 2, call_id, kind, video, state, started_by, end_reason, duration_ms, started_at, end_at}`,
with a short plain message for other Mattermost clients. Relay maps it to `TelegramMediaAction.phoneCall`
(`direct`) or `.groupPhoneCall` (`group`/`channel`), so the chat shows Telegram's call service messages.

## Shared client core (`submodules/RelayCalls`)

- `RelayCallsCore` (Foundation only): call/config models above; `RelayCallsClient` with every route;
  `RelayCallsEvent.decode(eventName:data:)`; `RelayParticipantIdentity` (`<user id>:<device id>`).
- `RelayCalls` (LiveKit): `RelayRoomEngine` (connect/disconnect, microphone, camera, screen share, participant
  snapshots with speaking/audio level/track sids/connection quality, change callback, adaptive stream + dynacast,
  H.264 preferred so remote frames decode to `CVPixelBuffer`); `RelayVideoSink` (a LiveKit `VideoRenderer` that
  hands frames to a callback: `CVPixelBuffer` plus rotation, or I420 planes); an external-camera publisher fed with
  pixel buffers (iOS reuses Telegram's own `OngoingCallVideoCapturer`); `RelayDirectCall` and `RelayGroupCall`
  controllers (UI-free state machines over the client, events and the engine); CallKit audio hooks for iOS.

## Platform adapters

**iOS** (new `RelayCallsTelegram` target): `RelayCallManager: PresentationCallManager` (requests, incoming rings from
events and VoIP pushes, CallKit), `RelayPresentationCall: PresentationCall`, `RelayPresentationGroupCall:
PresentationGroupCall`, LiveKit→`VideoFrameData` adapter (needs a public init in TelegramVoip), audio through
`ManagedAudioSession` with LiveKit's engine gated by CallKit activation. Patches: a `PresentationCallVideoProviding`
protocol replacing the `as! PresentationCallImpl`/`PresentationGroupCallImpl` casts in `VideoChatScreen` and
`CallControllerNodeV2`; public CallKit setup gated on `MattermostFeatures.relayCalls`; a no-device mode for
`SharedCallAudioContext`; the Relay manager created in `SharedAccountContext` when Mattermost is on; join-panel data
from MattermostSync; no emoji key when there is no key; PushKit branch in `AppDelegate`, `voip` background mode.
Remove `.relayCall` and the SwiftUI window.

**macOS** (new `packages/RelayTelegramCalls`): `LiveKitVideoSource: VideoSource`, `RelayPresentationGroupCall:
PresentationGroupCall` (macOS protocol) for `GroupCallContext`, `RelayPeerCallSession` behind a new
`PresentationPeerCall` protocol extracted from `PCallSession` uses (call screen glue, navigation header, shared
context hooks); incoming rings in `SharedWakeupManager` from MattermostSync events; group hooks in
`ChatUIHooksInstall`. Fix `PrivateCallScreen/Package.swift` resources (`.copy` → `.process`; the likely cause of
the old Call crash). Remove `RelayCallWindow` and the forced call buttons.

Telegram features with no Relay backing stay hidden (`canManageCall`/invite links/recording/scheduling/in-call
messages/join-as): adapters return empty or `nil` for them.

## Phases

1. Plugin v2 (contract above, Go tests) and the shared core (models, client, events, engine, controllers,
   MattermostSync events/active call/call records/callable users). In parallel.
2. iOS and macOS adapters. In parallel, on different repositories.
3. Local integration on the dev server (OrbStack `mmdev` + a LiveKit dev container + plugin v2): macOS client and
   the dedicated simulators. Ringing over WebSocket; camera on macOS (the iOS Simulator cannot publish a camera).
   Then physical iPhone for CallKit, VoIP push and camera when the owner wants it.
4. Side-by-side review against Telegram's real screens; fix differences.
