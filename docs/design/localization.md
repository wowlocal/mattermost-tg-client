# Localization

Status of Relay's languages, the options for more, and the build mechanism that a translation plugs into
(Phase 4C). Relay ships in English only; this is the groundwork, not a translation.

## Current state

**Where texts come from.** Every UI text of Telegram's code and Relay's own screens is a `PresentationStrings`
accessor (`presentationData.strings.Relay_Threads_Title`), generated from one `.strings` file:

1. `Telegram/Telegram-iOS/en.lproj/Localizable.strings`: upstream's English, untouched (13,500 keys).
2. `Telegram/Telegram-iOS/Relay.strings`: Relay's overlay. It replaces upstream values that name Telegram on
   surfaces Relay keeps ("Relay Cache", the permission texts) and adds Relay's own keys (`Relay.*`, ~400).
3. The genrule `RelayLocalizableStrings` (Telegram/BUILD, `build-system/GenerateStrings/MergeStrings.py`) merges the
   two; a key in the overlay wins. `GeneratedPresentationStrings` turns the merged file into the accessors and a
   key table; the app bundle ships the merged file as `en.lproj/Localizable.strings`.

At runtime the values are read from that bundled file (`defaultPresentationStrings`), or from a language pack in
`LocalizationSettings`. A key missing from the pack falls back to the bundle's English (`getSingle` in the
generated `PresentationStrings.m`; plural forms fall back the same way).

**Telegram's other languages were never in the app.** Telegram-iOS downloads language packs from Telegram's
servers (`langpack.getLangPack`, Settings → Language). Relay never talks to Telegram, so it has no packs, and the
Language row is hidden (Phase 1). The 18 `<lang>.lproj/Localizable.strings` files upstream bundles (ar, be, ca,
de, es, fa, fr, id, it, ko, ms, nl, pl, pt, ru, tr, uk, uz) are **empty** (generated by `touch`). They only make iOS
treat the app as localized into those languages: system UI the app shows (photo picker, share sheet, text menus)
follows the device language, and Settings → Relay → Language lists them.

**Texts outside `Localizable.strings`:**

| Text | Where | Language today |
|---|---|---|
| Permission prompts (camera, photos, location, …) | `Telegram-iOS/en.lproj/InfoPlist.strings` (`InfoPlistStringResources`) | English only: upstream's other languages name the app "Telegram" |
| Share extension sign-in alert | `Telegram/Share/en.lproj/Localizable.strings` (2 keys) | English |
| Notification extension placeholder ("You have a new message") | `MattermostPushService` | English literal (the extension has no strings) |
| Service messages ("bob joined the channel."), "(Only visible to you)" | composed by MattermostSyncCore / MattermostSync when a post is stored | English, **stored** in the message text |
| Write-failure toasts ("Couldn't send the message: …") | `MattermostNotice` (MattermostSync), worded by MattermostUI's `relayNotice` | `Relay.Notice.*` since 4C; the error detail is the server's or the system's text |
| Server texts (error messages, slash command help, system admin texts) | the Mattermost server | the server's language |
| Dates, times, numbers | `DateFormatter`, `PresentationDateTimeFormat` | the device's region (already localized) |

## Options for more languages

1. **Bundle Telegram's translations.** Telegram's community translates Telegram-iOS on translations.telegram.org;
   a pack could be exported once and dropped in as `<lang>.lproj/Localizable.strings`. It covers all of Telegram's
   UI that Relay keeps. Costs and unknowns:
   - **Licensing is unknown.** The translations are contributed by volunteers through Telegram's platform; no
     license for reuse outside Telegram's apps was found in the repository or the pinned commit. *Needs checking
     (legal) before any pack is bundled; do not assume they are covered by the source license.*
   - Every pack names "Telegram" where Relay's English overlay says "Relay", so each language also needs Relay's
     overrides translated (the build enforces it, below).
   - Packs follow Telegram's key set at the time of export; keys added since fall back to English.
2. **Per-language Relay overlays only** (`<lang>.lproj/Relay.strings`, ~400 keys): Relay's own screens and the
   overridden texts in the language, everything of Telegram's in English. Cheap, but the app is visibly mixed.
3. **Relay's own translation of the kept surfaces**: translate Relay's keys plus the upstream keys reachable from
   the screens Relay keeps (about a third of upstream's keys are hidden features: Premium, Stars, stories, calls,
   …). Best result; needs a key inventory per screen and a translation workflow (export the English, import
   translations as `<lang>.lproj/*.strings`).

Any option also needs, per language: `InfoPlist.strings` (permission prompts, App Store review reads them) and the
texts composed by the sync (render service messages from a stored action instead of stored English text: store the
`ServiceAction` in a message attribute and word it in the bubble). MattermostSync's toasts already go through the
strings (`MattermostNotice`, 4C).

## The mechanism (implemented)

**Build** (Telegram/BUILD, `relay_translated_languages`). A language is bundled with strings of its own when
`Telegram/Telegram-iOS/<lang>.lproj/` contains

- `Relay.strings`: Relay's keys and Relay's overrides of upstream keys, translated; and/or
- `Localizable.strings`: a full translation of upstream's English file (option 1).

For each such language a genrule `RelayLocalizableStrings_<lang>` merges the two exactly like English and replaces
the empty stub (or adds a new `<lang>.lproj`, e.g. `ja`). The merge checks the result against the merged English
and **fails the build** when

- a key doesn't exist in English (typos; a plural form like `_3_10` only needs its key's plural family in English);
- a value uses a positional argument English doesn't have for that key (`%3$@` where English has two): the
  generated accessors fill arguments by index, so that would read past them. Reordering (`%2$@ … %1$@`) is fine;
- a full translation contains a key Relay overrides in English but the language's `Relay.strings` doesn't
  override it (the translation's "Telegram" wording would otherwise win over Relay's).

**Runtime** (`TelegramPresentationData/Sources/RelayBundledLocalization.swift`). `defaultPresentationStrings` (the
strings every screen starts from while no server pack is set, which in Relay is always) is the bundled language
the user prefers: `Bundle.preferredLocalizations(from:)` over the bundled localizations that have strings, matched
against the user's languages, so **the iOS per-app language (Settings → Relay → Language) or the device language
picks it**. English otherwise. Keys the language lacks fall back to English per key. Only with
`MattermostBackend.isEnabled` (upstream builds keep their behaviour). The share extension reads the same bundled
file through `getAppBundle()`.

**Adding a language**

1. Create `Telegram/Telegram-iOS/<lang>.lproj/Relay.strings` (copy `Relay.strings`, translate the values; keep
   the keys and the `%@`/`%1$@` arguments). For option 1 also add `<lang>.lproj/Localizable.strings`.
2. Build. Fix what MergeStrings reports.
3. Run with the language: Settings → Relay → Language on the device, or
   `xcrun simctl launch <udid> org.relaychat.Relay -AppleLanguages "(<lang>)"`.
4. Not covered by the mechanism yet: `<lang>.lproj/InfoPlist.strings` (add the file and list it in
   `InfoPlistStringResources`), the extensions' own files, texts composed by the sync (see above).

Checked in 4C with a temporary `de.lproj/Relay.strings` of 12 keys (not committed): the build merged it into
`de.lproj/Localizable.strings`, and with `-AppleLanguages "(de)"` the threads screen read "4 UNGELESEN · 2
ERWÄHNUNGEN", "55 Antworten", "1 neue Antwort", with English for the keys the file lacked
(`docs/research/phase4c-lang-de.png`). A key that isn't English, an extra `%3$@`, or a full translation without
Relay's overrides stopped the merge with a message naming the key.

## Pseudo-language (debug builds)

Debug builds also bundle **`en-XA`**, generated from the merged English by
`build-system/GenerateStrings/PseudoLocalizeStrings.py` (genrule `RelayPseudoLocalizableStrings`; `AppStringResources`
selects it only for `compilation_mode=dbg`, so release builds don't ship it). Every value is accented, about a third
longer (doubled vowels, so words still wrap like words) and bracketed: "Log In" → "⟦Ļööĝ Îîñ⟧". Format arguments,
escapes, `{placeholders}`, markdown link targets and URLs are kept.

```sh
xcrun simctl launch <udid> org.relaychat.Relay -AppleLanguages "(en-XA)"
```

On screen, plain English is a hard-coded text (or server data), a missing "⟧" is a clipped label, and the extra
length shows where longer languages would truncate.

Findings (4C, with a search of Relay's code): the login divider "or", the login id placeholder, the login footer,
"Mark as Read", MattermostSync's failure toasts (now `MattermostNotice`, worded by MattermostUI), Mattermost's
suggested custom statuses, the table block title, generic device names, and Telegram's checkbox value "Selected"
were English literals; all now come from the strings. Still English by design: server data (names, posts, channel
purposes, the server's own error messages) and the texts the sync stores (above). Screenshots
`docs/research/phase4c-pseudo-*.png`.

## Right-to-left

Telegram-iOS does not mirror its layouts for right-to-left languages: screens keep their left-to-right
structure, and text nodes align right-to-left text naturally. Relay's screens follow the same model (manual
layouts in Display/AsyncDisplayKit; UIKit controls such as the login text fields align by the text's direction).
A full RTL layout would be an upstream-wide change. Checked in 4C with the Arabic locale and with right-to-left
content; see PROGRESS.md.
